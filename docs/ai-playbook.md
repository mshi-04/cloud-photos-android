# AIプレイブック

このドキュメントは、AIエージェントがこのリポジトリでどのように作業すべきかを説明します。
ワークフローガイドであり、ルールセットではありません。ルールは `AGENTS.md` にあります。

## 1. 着手前に読む

変更を行う前に、以下の順序でファイルを読むこと：

1. `AGENTS.md` — すべてのルールの情報源
2. `app/AGENTS.md`、`core/AGENTS.md`、`feature/<name>/AGENTS.md` — 触れるエリアのローカル補足
3. `CLAUDE.md` — Claude向けエントリーガイダンスとスタック概要
4. `.agent/skills/*` — 必要なパターンカテゴリのスキルファイル

ガイダンスが矛盾する場合は、リストの上位を優先し保守的に留まること。

## 2. コーディング前の確認

- 影響を受ける単一の最小モジュールを特定する。
- 正しいレイヤー（`domain`、`data`、または `ui`）を確認する。
- 同じフィーチャーの既存ファイルを少なくとも1つ読み、命名とパターンを把握する。
- 同じフィーチャーに同等のものがすでに存在する場合、新しい抽象化を作らない。

## 3. コードをどこに置くか

この決定木を使用する：

| 何であるか                                                   | どこに置くか              |
|--------------------------------------------------------------|---------------------------|
| ビジネスルール、ユースケース、値オブジェクト                 | `feature:<name>:domain`   |
| リポジトリ実装、データソース、マッパー、DAO、ワーカー        | `feature:<name>:data`     |
| ViewModel、UIステート、Composeスクリーン                     | `feature:<name>:ui`       |
| フィーチャー横断の共有抽象化（再利用がすでに正当化済み）     | `core:*`                  |
| アプリエントリ、ナビゲーション、Hilt配線                     | `app`                     |

迷ったときは、すでにいるフィーチャーレイヤーに変更を留める。

## 4. 変更を小さく保つ

- 必要最小限のファイルに触れる。
- フィーチャー実装中に無関係なコードをクリーンアップしない。
- タスクが明示的に要求しない限りパッケージを移動しない。
- より広い変更が必要に見える場合は、サイドエフェクトとしてではなく、フォローアップ項目として提示する。

## 5. 検証：何をいつ実行するか

完全なポリシーは `docs/verification-policy.md` を参照。

短い要約：

- **開発中**：単一の影響モジュールのテストを実行する。
- **PR前**：`ktlintCheck detekt` と影響モジュールのテストを実行する。
- **CIが最終ゲート**：マージ前にすべてのリポジトリCIチェックがパスしなければならない。

ソースのみの変更の後にGradleシンクは不要。

## 6. PRを開く前のチェックリスト

- [ ] lintパス：`./gradlew ktlintFormat && ./gradlew ktlintCheck detekt`
- [ ] 変更モジュールのテストパス
- [ ] ハードコードされたシークレット、エンドポイント、バケット名がない
- [ ] デバッグログや `android.util.Log` 呼び出しがコミットされていない
- [ ] レイヤー横断の依存違反が導入されていない
- [ ] `CancellationException` が握り潰されていない

## 7. レポート形式

標準形式については `AGENTS.md` §「AI生成変更の必須レポート形式」を参照。

すべての変更について以下でレポートすること：

```text
変更したモジュール: <一覧>
ファイル配置のアーキテクチャ的理由: <各ファイルがそのレイヤーにある理由>
概要: <何をなぜ変更したか>
実行したテスト: <コマンドと結果>
実行しなかったテスト: <コマンドと理由>
既知の制限または今後の対応項目: <既知の制限や次のステップ>
```

テストを実行しなかった場合は、明示的にその旨を記載すること。

## 8. 補足リファレンス

関連する場合に参照すること：

| ドキュメント                       | いつ読むか                                                                    |
|------------------------------------|-------------------------------------------------------------------------------|
| `docs/media-upload-flow.md`        | ワーカー、スケジューラ、SyncStatus、アップロード/削除ユースケースを変更する前 |

## 9. やってはいけないこと

以下を避けること — 理由付きの完全なリストは `docs/forbidden-patterns.md` を参照：

- プロダクションコードに `android.util.Log`
- 一時的なデバッグログのコミット
- UIが `data` 実装を直接呼び出す
- `domain` にAndroid/Compose/Room
- UIへのDTOやエンティティの返却
- `RepositoryImpl` へのビジネスロジックの蓄積
- 暗黙の大規模リファクタリング
- ハードコードされたシークレットやエンドポイント
- `CancellationException` の握り潰し
- 軽率なフィーチャー横断依存

## 10. Git操作の所有権

ユーザーが明示的に要求しない限り、Git操作はユーザーが所有する。
ユーザーが明示的に要求しない限り、コミット、プッシュ、ブランチ作成、プルリクエスト作成は行わない。
コード変更、検証、レポートに集中する。

## 11. プルリクエストとブランチのワークフロー

ユーザーがGit操作を明示的に要求した場合に適用される：

- 明示的に別のブランチを指示されない限り、フィーチャー作業は `develop` からブランチを切る。
- 保護されたブランチに直接プッシュしない。
- PRのスコープはブランチの目的と一致させ、コンパクトに保つ。
- テストノートやAndroid固有のチェックを含む、リポジトリのPRテンプレートの期待に従う。

## 12. 変更戦略（クイックリファレンス）

何かを実装するよう求められた場合、この順序に従う：

1. 影響を受ける最小のモジュールを特定する。
2. ロジックの正しいレイヤーを確認する。
3. まず同じフィーチャーの既存パターンを再利用する。
4. 最小限の安全な変更を行う。
5. ターゲットを絞った検証を実行する。
6. 何が変わったか、何が変わらなかったか、残存リスクを正確にまとめる。

各ステップの詳細は上記セクション1〜7を参照。

## 13. サブエージェントポリシー

このセクションはマルチエージェントワークフロー、主にClaude Codeサブエージェントを管理します。
サブエージェントは実装を並列化する手段ではなく、ミスを減らすためのサポートツールです。

### 原則

- 親エージェントがすべての最終決定を所有する：設計、ファイル配置、編集、レポート。
- サブエージェントは調査と検証を行う。独立して実装しない。
- 小さくローカルな変更にサブエージェントは不要。単純なタスクにマルチエージェントワークフローを強制しない。
- 各サブエージェントへの委譲は狭く明示的でなければならない。何を確認・調査するかを正確に記述する。

### 良い使い方

- 影響スコープの確認：提案する変更の影響を受けるモジュール、ファイル、テストの特定。
- 既存パターンの調査：同じフィーチャーが同様の関心事をどのように処理しているかの調査。
- ルール準拠レビュー：`AGENTS.md`、`docs/forbidden-patterns.md`、レイヤー配置ルールに対するドラフト変更の確認。
- 検証ターゲットの特定：実行すべきGradleテストターゲットの決定。
- アーキテクチャバリデーション：編集前のモジュール境界と依存方向の確認。

### 悪い使い方

- 複数のファイルやモジュールにまたがる広範な並列実装。
- 明確なユーザー要求のない投機的なリファクタリング。
- 複数のサブエージェントによる同一ファイルの並行編集。
- 親の監視なしにサブエージェントに委譲されたフィーチャー横断の再設計。
- 未解決の設計上の質問をユーザーに提示せずサブエージェントに転送すること。

### 親エージェントの責任

1. まず最小限の安全な変更を決定する（セクション12）。
2. 委譲する狭い質問を決定する（もしあれば）。
3. 最終編集をサブエージェントに委ねない — サブエージェントの知見をレビューした後に変更を適用する。
4. サブエージェントの出力を一つの一貫したレポートに統合する（セクション7）。
5. アーキテクチャと配置の決定を保持する。サブエージェントはモジュール境界（`app`、`core:*`、`feature:*`）を移動しない。

### サブエージェントスコープの制約

- サブエージェントは、明示的に調査するよう指示されていないモジュールのファイルを編集してはならない。
- サブエージェントは新しい抽象化の導入、パッケージの移動、依存配線の変更を行ってはならない。
- サブエージェントはコミット、プッシュ、破壊的なコマンドを実行してはならない。
- サブエージェントがタスクが想定より広いことを発見した場合、自分のスコープを広げるのではなく親エージェントに報告しなければならない。

### 利用可能なプロジェクトサブエージェント

プロジェクトレベルのサブエージェント定義は `.claude/agents/` にあります：

| エージェント     | 目的                                           | 書き込みアクセス  |
|------------------|------------------------------------------------|-------------------|
| `reviewer`       | アーキテクチャ、セキュリティ、規約レビュー     | なし（読み取り専用）|
| `test-writer`    | プロジェクトパターンに従ったユニットテスト生成 | あり              |
| `arch-checker`   | モジュール境界と依存方向のバリデーション       | なし（読み取り専用）|

これらのエージェントは内部で `AGENTS.md` と `docs/` を参照します。
このリポジトリの規約に事前スコープされています。
